# Rubric

Writers put `::: words` directives in Markdown; Jev (TypeSafe's model) picks a part from a human-designed catalog; Hugo renders it. Read `docs/plan.md` for the product and the order of work, and `docs/lsp.md` for the slice that is built: the language server, the Neovim plugin, what the live Jev probe found, and what the live test found.

## Commands

- `bun test` runs everything, including a real headless Neovim (`test/nvim.test.ts`) with the stub resolver. `UPDATE=1 bun test test/fixtures.test.ts` rewrites fixture expectations.
- `bun run typecheck`.
- `rubric` is on the PATH through `bun link` (the package's `bin`). Opening a page of `testing/` in Neovim starts its process, which serves it at http://127.0.0.1:1415 with the cursor relay on 1416; `rubric` in a terminal does the same in front, `rubric stop` stops it, `rubric watch` prints every call to Jev as a table, `rubric new <folder>` makes a site and `rubric build` publishes one into `public/`. `testing/README.md` has the keys. The tests run site processes with `RUBRIC_HUGO` (a stand-in), `RUBRIC_IDLE_MS` and their own `XDG_RUNTIME_DIR`.
- `bun scripts/theme.ts build|check|look|new` builds a catalog's themes from their pieces in `themes/`, checks them, draws them in a browser at three widths (pictures in `catalogs/<catalog>/shots/index.html`; all 71 take about 10 minutes, `look <theme>…` draws fewer), and starts new pieces. `RUBRIC_CATALOG` names the catalog, universal by default. Never edit `assets/css/palettes|pairings|scales/`; they are generated. Parts and `base.css` read slots only. The plan's "How a theme is made" has the design.
- `bun scripts/probe.ts [lines.yaml]` runs lines against the live Jev API and saves each run under `probe/runs/`. Ask before running it; it costs money and uses the key.
- `bun scripts/bench.ts run|draw` drafts the requests in `bench/requests.txt` with several drafters (`--drafters opus:low,openai/gpt-6.1-sol:low`; a model with a provider in its name goes through OpenCode, which reports no cost on a plan) and draws them side by side in `bench/runs/<run>/index.html`, with time, cost and Jev's look at each picture; use it to measure a change to the brief, its examples or the default drafter. A run costs about $1: ask first. `draw <run>` redraws one for cents.
- `bun scripts/pause.ts` replays the writer's typing (`testing/.rubric/keys.jsonl`, logged while `rubric watch` runs) and compares pauses before a line is asked: calls, half-typed calls, and the wait.
- `bun scripts/live-repro.ts [blocks] [msPerKey]` types blocks through the user's real Neovim config and compares the buffer, the server's text, `content/` and what Hugo serves. `RUBRIC_HOLD=<ms>` keeps the page up for a browser check. It reads the page's port from `testing/.rubric/serve.json`.

## Rules

- Write American English everywhere: code, catalog values and descriptions, CSS classes, docs, tests, sample writing, commit messages (`center`, `color`, `gray`, `behavior`, `-ize`, `flashlight`, `sidewalk`). A spelling in a catalog value or description is part of what Jev reads, so changing one bumps the catalog's version.
- `.env` holds `TYPESAFE_API_KEY`. Never read, print or commit it. The server runs with the repo as its working directory so Bun loads it.
- Jev is pinned to `jev-1.14.0` in `src/core/questions.ts`. Question wording and thresholds live there and nowhere else. The TypeSafe SDK is used for types only; calls go through `fetch` in `src/jev.ts` because the SDK breaks under Bun.
- The server works from the editor's text, never the saved file, and writes only `content/` and `.rubric/`, with one exception: when the writer keeps a drafted part, it writes the site's `parts/<name>/`, or, for every theme, the catalog (`src/parts.ts`). Files are written whole, through `src/core/write.ts`.
- Text the writer sees (menu entries, notes, notices, ghost text) states the action or the fact in as few words as carry it: "Reroll", "Similar parts (4)", "no log yet". It never talks to the writer: no "Just …", "Yes, …", "Look at the ones you already have", "your", "please", questions, or advice on what to do meanwhile.
- Diagnostics carry a `Code` from `src/core/diagnostic.ts`; add to that union before using a new one.
- The Neovim plugin is `editors/nvim/`, loaded by the user's dotfiles from this path. Do not edit the dotfiles repo without being asked.
- `testing/TESTING.md` is the user's live-test checklist. Update it in the same change as anything they could test by hand: what is new, what to try, what should happen.
- What is tracked in `testing/` is the fixture the tests copy. The user's own test writing stays local: new parts in `testing/parts/`, their pictures and `moms-blog.md` are ignored, and their edits to `testing/pages/posts/walk.md` and `testing/rubric.md` are hidden with `git update-index --skip-worktree` (undo with `--no-skip-worktree` to commit a change to either). Never add those to a commit unasked.
- The user tests by hand in Neovim and writes findings in the Notes section at the bottom of `testing/TESTING.md`. Reproduce a reported problem through the real config before theorizing; `scripts/live-repro.ts` is the pattern.
